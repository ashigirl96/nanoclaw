# LLM Wiki

> 出典: [karpathy/llm-wiki.md](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

LLM（大規模言語モデル）を使って、個人向けの知識ベースを構築するためのパターンである。

これは「アイデアファイル」である。OpenAI Codex（OpenAI のコーディング用エージェント）、Claude Code（Anthropic のコーディング用エージェント）、OpenCode（オープンソースのコーディング用エージェント）、Pi（コーディング用エージェントの一つ）など、自分の LLM エージェントにコピーして使うことを想定している。目的は大まかな考え方を伝えることで、細部はエージェントがユーザーと協働して組み立てる。

## 中心となる考え方

LLM と文書のやり取りの多くは RAG（検索で関連する断片を取り出し、それをもとに回答を生成する方式）に従う。ファイルをアップロードし、問い合わせのたびに関連する断片を取り出して回答を作る。知識は質問のたびに組み立て直され、蓄積されない。

ここでの考え方は根本的に異なる。原資料を都度検索するだけでなく、LLM が原資料とユーザーの間に永続的な wiki を少しずつ作り、保守する。この wiki は、構造を持ち相互にリンクされた Markdown（見出しや箇条書きを記号で書く軽量な文書形式）の集まりである。新しい資料を加えると、LLM はその資料を読んで要点を抜き出し、既存の wiki のページに統合する。エンティティ（人・組織・概念など、ページの対象となるもの）のページを更新し、要約を改訂し、矛盾を指摘し、統合された見解を強化する。知識は一度まとめられ、問い合わせのたびに組み立て直す必要なく、最新の状態を保つ。

wiki は、積み上がっていく永続的な成果物になる。相互参照はあらかじめ存在する。矛盾には印が付く。統合された見解は、読んだ内容すべてを反映する。wiki は、資料を加えたり問いを投げたりするたびに充実していく。

ユーザーは資料を集めて問いを投げ、LLM がそれ以外のすべて（要約、相互参照、分類、整理）を担う。LLM はプログラマー、Obsidian（Markdown を編集・閲覧するノートアプリ）は IDE（統合開発環境）、wiki はコードベースの役割を果たす。

**主な用途：**
- 個人: 目標、健康、自己改善の追跡
- 研究: 数週間から数か月にわたる深掘り
- 読書: 本を読み進めながら、伴走用の wiki を作る
- 業務・チーム: Slack（チャットツール）、書き起こし、文書から取り込んだ社内 wiki
- 分析: 競合調査、デューデリジェンス（投資や買収の前に行う詳細な調査）、旅行計画、趣味の深掘り

## 構成

このシステムは三つの層から成る：

**原資料** — 厳選された、変更されない文書（記事、論文、画像、データ）。LLM はこれらを読むだけで、決して書き換えない。

**wiki** — LLM が生成した Markdown のディレクトリで、要約、エンティティのページ、概念のページ、比較、統合の結果を含む。LLM がこれを全面的に所有し、相互参照と一貫性を保ちながらページを作成・更新する。

**スキーマ** — wiki の構成、約束事、取り込み・問い合わせ・保守の手順を説明する設定文書（例: CLAUDE.md。Claude Code が読む指示用の Markdown ファイル）。この鍵となるファイルによって、LLM は汎用のチャットボットではなく、規律を守る wiki の保守者になる。

## 運用

**取り込み：** 新しい資料を原資料の置き場に入れると、LLM がそれを処理する。エージェントは資料を読み、要点を話し合い、要約を書き、索引を更新し、エンティティと概念のページを更新し、記録を追記する。1 件の資料が 10〜15 ページの wiki に波及することもある。ユーザーが関わりながら 1 件ずつ取り込むのが望ましいが、監督を減らしてまとめて取り込むことも可能である。

**問い合わせ：** wiki に対して質問する。LLM は関連するページを検索し、出典を付けて回答をまとめる。回答の形式は、Markdown のページ、比較表、スライド資料、グラフ、canvas（自由に配置できる作業画面）などさまざまである。良い回答は新しいページとして wiki に書き戻せる。こうして探索の成果は、チャットの履歴に消えることなく、知識ベースの中で積み上がる。

**健全性点検：** 定期的に wiki の健康状態を点検する。矛盾、新しい資料に置き換えられた古い主張、内向きのリンクがない孤立したページ、専用のページがない重要な概念、相互参照の欠落、データの欠落を探す。LLM は調べるべき事項と追うべき資料を提案し、wiki が大きくなっても健全な状態を保つ。

## 索引と記録

大きくなっていく wiki の中を見て回りやすくするため、特別なファイルが二つある：

**index.md** — すべての内容のカタログ。各ページのリンク、一行の要約、日付や資料数などの任意のメタデータを、カテゴリごとに並べる。LLM は取り込みのたびにこれを更新する。問い合わせに答えるときは、まず index.md を読んで関連するページの位置を特定してから、深く掘り下げる。この方式は中規模（資料およそ 100 件、ページ数百件程度）で驚くほどうまく機能し、埋め込み（文を数値のベクトルに変換して近さで探す仕組み）に基づく RAG の基盤を用意する必要がない。

**log.md** — 何がいつ起きたかを時系列で追記するだけの記録（取り込み、問い合わせ、健全性点検の実行）。各項目は決まった接頭辞で始まる（例: `## [2026-04-02] ingest | Article Title`）ので、単純なツールで解析できる。`grep "^## \[" log.md | tail -5` で末尾の 5 件が得られる。この記録は wiki の変化の時系列を示し、LLM が直近の活動を把握する助けになる。

## 任意: CLI ツール

規模が大きくなると、小さなツールが LLM の作業効率を上げる。wiki のページを検索する検索エンジンが最も分かりやすい例である。小規模なら索引で足りるが、wiki が大きくなると本格的な検索が必要になる。qmd（https://github.com/tobi/qmd）は端末内で動く検索ツールで、BM25（キーワードの一致度で並べる検索方式）とベクトル検索を組み合わせ、LLM による再順位付けを加える。すべて端末内で動く。CLI（コマンドラインから操作するツール）と MCP サーバー（LLM に道具を提供するサーバー）の両方を備えており、LLM はシェルから呼ぶことも、ツールとして直接使うこともできる。必要に応じて、より単純な検索スクリプトを自作すればよい。

## ヒントと工夫

- Web の記事を Markdown に変換する **Obsidian Web Clipper** で、資料を手早く集める。
- **画像をローカルに保存:** Obsidian の設定画面（Settings）で添付ファイルのフォルダーを指定し、ダウンロード用のホットキーを割り当てる。画像はすべてローカルに保存され、LLM は壊れるかもしれない URL に頼らず、画像を直接見て参照できる。
- **Obsidian のグラフビュー** は wiki のつながりを図にする。どのページがどこにつながるか、ハブとなるページ、孤立したページが分かる。
- **Marp**（Markdown からスライドを作るツール）は、Obsidian のプラグインとして連携できる。
- **Dataview**（Obsidian のプラグインで、ページ冒頭のメタデータ（frontmatter）を問い合わせる）は、LLM が YAML（設定データの記法）でメタデータを加えると、動的な表やリストを生成する。
- wiki は、git（版管理ツール）で管理された Markdown のディレクトリにすぎない。版の履歴、branch による分岐、共同作業もそのまま備わる。

## なぜうまくいくのか

知識ベースの保守で面倒なのは、読むことや考えることではなく、相互参照の更新、要約の最新化、データの矛盾の書き留め、ページ間の一貫性の維持といった雑務である。保守の負担が価値を上回ると、人は wiki を見捨てる。LLM は飽きず、更新を忘れず、一度に 15 ファイルへ手を入れられる。wiki の保守は、ほぼ無料になる。

人は資料を厳選し、分析の方向を決め、良い問いを立て、意味を考える。それ以外は LLM が引き受ける。

この考え方は、Vannevar Bush が 1945 年に構想した Memex（個人が厳選した知識を蓄え、文書同士の連想をたどれるようにした装置）と精神において通じる。Bush の構想は、現在の Web よりもこれに近い。私的で、能動的に厳選され、文書同士のつながりが文書そのものと同じくらい価値を持つ。Bush は保守の問題を解けなかったが、それを LLM が担う。

## 注記

この文書は具体的な実装ではなく考え方を述べるため、あえて抽象的なままにしてある。ディレクトリ構成、スキーマの約束事、ページの形式、道具立ては、分野、好み、選んだ LLM によって決まる。何もかもが任意で、部品のように取り外せる。役に立つものを選び、そうでないものは無視すればよい。資料がテキストだけなら、画像を扱う必要はない。wiki が小さいままなら、索引ファイルで足り、検索エンジンは要らない。出力の形式をまったく変えたいかもしれない。この文書を LLM エージェントに渡し、協働して自分の必要に合う版を作ればよい。この文書の唯一の目的は考え方を伝えることであり、残りは LLM が考え出す。
